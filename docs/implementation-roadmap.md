## 文档职责

本文件是项目实现目标的**单一状态入口**，用于回答：

1. 哪些目标已经进入 `main` 并完成必要验证；
2. 哪些目标只在独立任务分支完成，尚未集成；
3. 哪些目标已经批准、仍是提案、依赖外部输入或被证据判定为 NO-GO；
4. 每个目标达到什么验收条件后才能改变状态。

[`product-spec.md`](product-spec.md) 继续定义产品范围与成功标准，[`architecture.md`](architecture.md) 定义模块与数据边界；本文件不复制它们的详细规则，只跟踪交付状态和证据。研究、计划、任务分支测试、浏览器截图或接口可访问都不能单独算作“已完成”。

## 状态定义

| 状态 | 是否算完成 | 精确定义 |
|---|---:|---|
| `INTEGRATED` | **是** | 已进入目标主分支，变更范围与提交关系已核对，并完成与风险匹配的主分支复验 |
| `READY_ON_BRANCH` | 否 | 独立任务分支已形成提交且通过分支验证，但尚未合并到目标主分支 |
| `IN_PROGRESS` | 否 | 已获批准并正在独立任务分支实施，尚未达到分支交付门槛 |
| `APPROVED_NOT_STARTED` | 否 | 目标和边界已明确批准，但尚未开始实现 |
| `PROPOSED` | 否 | 有明确价值与初步验收口径，但尚未获得实施批准 |
| `BLOCKED` | 否 | 目标成立，但缺少用户输入、权限、正式数据、外部服务或其他必要前提 |
| `NO_GO` | 否 | 当前证据明确不足或风险不可接受；解除条件满足前不得实现运行时能力 |
| `OUT_OF_SCOPE` | 不适用 | 当前产品边界明确排除；若要纳入，必须先修改产品范围和风险约束 |

只有 `INTEGRATED` 计入“已完成”。`READY_ON_BRANCH` 不得在汇报中简称为“完成”，避免把本地任务分支、`main` 和远端状态混为一谈。

## 状态维护规则

每个后续任务都必须更新本文件，遵守以下顺序：

1. **任务开始前**：确认或新增稳定目标 ID，写清验收条件，把获批准目标改为 `IN_PROGRESS`；
2. **分支验证通过后**：改为 `READY_ON_BRANCH`，记录任务分支、提交、已运行验证和未执行验证；
3. **合并后**：只有在目标主分支核对提交关系、工作区和变更范围，并完成必要复验后，才能改为 `INTEGRATED`；
4. **证据不足时**：使用 `BLOCKED` 或 `NO_GO`，记录解除条件，不能用空实现、模拟数据或静默降级制造“已完成”；
5. **范围变化时**：更新验收条件和状态日期；旧目标 ID 不复用给不同能力；
6. **远端状态**：本地集成、远端推送、PR 和发布分别记录，不能相互推导；
7. **验证措辞**：明确区分自动测试、构建、浏览器验收、真实交易时段观察、外部授权和生产验证。
